# Phở Simulator — Vertical Slice Technical Architecture

Status: **M1 deliverable, frozen contract.** This document is the source of
truth for the vertical slice architecture. Later agents code against it;
changes to anything marked "frozen" go through the integration agent, not
ad hoc edits.

## 0. Governing constraints that drove every decision

| Constraint | Design consequence |
|---|---|
| AI agents author code; human playtests | Logic must be verifiable **without opening Unity**. Hence a pure-C# core + `dotnet test` harness. |
| MCP calls are round-trips, not version-controlled | Scenes/prefabs are **generated by C# editor scripts**. Committed `.unity`/`.prefab` are build outputs, not sources. |
| Only one Unity Editor can hold the project at a time | Parallelism happens at **code authoring**; compile/test verification is **serialized through one integration agent**. This is the hard ceiling on concurrency. |
| Unity YAML merges badly | Any conflict in `.unity`/`.prefab`/`.asset` → **delete and regenerate**, never hand-merge. |

### The two pure assemblies

`Pho.Domain.asmdef` — **this flag is the whole point**:

```json
{
  "name": "Pho.Domain",
  "references": [],
  "noEngineReferences": true,
  "overrideReferences": true,
  "precompiledReferences": ["Newtonsoft.Json.dll"],
  "autoReferenced": false,
  "allowUnsafeCode": false
}
```

`noEngineReferences: true` means the compiler **hard-errors** if an agent
types `Vector3`, `Debug.Log`, `MonoBehaviour`, or `[SerializeField]`. That is
the enforcement mechanism — not a code-review convention. `Pho.Save` gets the
same flag and references `Pho.Domain` only.

**What lives in `Pho.Domain` (pure):**

| Area | Types |
|---|---|
| Identity | `IngredientId`, `RecipeId`, `EquipmentId`, `ArchetypeId`, `OrderId`, `CustomerId` |
| Static-data contracts | `IIngredientDef`, `IRecipeDef`, `IEquipmentDef`, `ICustomerArchetype`, `IBalanceConfig`, `IGameDatabase` |
| Runtime state | `InventoryModel`, `Ledger`, `BowlContents`, `BrothState`, `OrderModel`, `CustomerBrain`, `RestaurantState`, `DayClock` |
| Pure logic | `RecipeMatcher`, `QualityCalculator`, `SatisfactionCalculator`, `BrothSimulator`, `PricingCalculator`, `OrderStateMachine`, `ReputationCalculator` |
| Infra | `EventBus`, `IGameEvent`, event structs, `Vec3`, `IClock` |

**How static data and interfaces relate, without duplication:** Domain
declares *interfaces*; `Pho.Data` ScriptableObjects *implement* them.

```csharp
// Pho.Domain — no UnityEngine
public interface IIngredientDef {
    IngredientId Id { get; }
    string DisplayName { get; }
    IngredientCategory Category { get; }
    float BasePurchasePrice { get; }
    float BaseQuality01 { get; }
    float ShelfLifeHours { get; }
    StorageRequirement Storage { get; }

}

// Pho.Data — Unity
[CreateAssetMenu(menuName = "Pho/Ingredient")]
public sealed class IngredientData : ScriptableObject, IIngredientDef { /* ... */ }
```

Domain tests instantiate trivial POCO fakes (`FakeIngredientDef`) — no Unity,
no assets, no `ScriptableObject.CreateInstance`.

### The `Tools/PhoDomain.Tests.csproj` trick

A standalone SDK-style csproj that globs
`../Assets/Scripts/Domain/**/*.cs` and `../Assets/Scripts/Save/**/*.cs`,
references NuGet `Newtonsoft.Json 13.0.3` + `NUnit` +
`Microsoft.NET.Test.Sdk`, and links `../Assets/Scripts/Tests/DomainTests/**/*.cs`.

```bash
dotnet test Tools/PhoDomain.Tests.csproj   # ~1s, no Unity process, no Library/ lock
```

Agents get sub-second red/green on roughly 80% of the game's actual logic
without touching the Editor. This is the single highest-leverage
architectural decision for an AI-driven build.

## 2. Core data models

### 2.1 Stable string IDs

```csharp
// Pho.Domain/Identity/IngredientId.cs
[JsonConverter(typeof(StringIdConverter<IngredientId>))]
public readonly struct IngredientId : IEquatable<IngredientId> {
    public readonly string Value;
    public IngredientId(string value) => Value = value;
    public bool IsEmpty => string.IsNullOrEmpty(Value);
    public override string ToString() => Value ?? "<none>";
    // Equals/GetHashCode via StringComparer.Ordinal
}
```

Typed IDs prevent "passed a recipeId where an ingredientId was expected" bugs.
The `JsonConverter` emits/reads a bare string, so save files stay readable:
`"ing.beef_brisket"`.

**ID conventions (enforced by an EditMode validation test):**
- Format `^[a-z]+\.[a-z0-9_]+$`, e.g. `ing.beef_brisket`, `rec.pho_tai`,
  `eq.burner_commercial`, `arc.office_worker`.
- ID is authored on the ScriptableObject and **must equal the asset filename**.
- IDs are **immutable once committed**. Renaming requires a save migration.
- `Pho.Data.Tests/ContentValidationTests` fails the build on: duplicate ID,
  ID/filename mismatch, malformed ID, dangling `IngredientId` reference in
  any recipe, ingredient not present in `GameDatabase`.

## 3. Event architecture — typed instance event bus in `Pho.Domain`

### The choice

| Option | Verdict |
|---|---|
| `static event Action` | Rejected. Leaks across PlayMode domain reloads, untestable in isolation, no ordering control. |
| ScriptableObject event channels | Rejected for this project specifically. Every channel is a `.asset` file → an MCP round-trip or hand-authored YAML per event, all merge-conflict-prone, none testable in a pure assembly. Contradicts the "reproducible from source, agent-authored" constraint. |
| **Typed instance event bus** | **Chosen.** Zero assets. Compile-time checked. Lives in `Pho.Domain`, so `EventBusTests` and all domain-logic tests run under `dotnet test`. |

### API

```csharp
// Pho.Domain/Events/IEventBus.cs
public interface IGameEvent { }                     // marker

public interface IEventBus {
    void Publish<T>(in T evt) where T : struct, IGameEvent;
    IDisposable Subscribe<T>(Action<T> handler) where T : struct, IGameEvent;
}

public sealed class EventBus : IEventBus {
    // Dictionary<Type, HandlerList<T>>; struct events → no boxing on publish path
    // Re-entrancy safe: mutations during dispatch are deferred to end of dispatch
    // Handler exceptions are caught, logged via an injected Action<Exception>, and
    //   do NOT abort the remaining handlers
}
```

Events are `readonly struct`, grouped **one file per feature area** so
agents adding events touch different files:

```csharp
// Pho.Domain/Events/KitchenEvents.cs
public readonly struct BowlAssembled : IGameEvent {
    public readonly int BowlInstanceId; public readonly RecipeId MatchedRecipe;
    public readonly float Accuracy01; public readonly float Quality01;
}
public readonly struct BrothReady : IGameEvent { public readonly float Quality01; }

// Pho.Domain/Events/OrderEvents.cs
public readonly struct OrderPlaced       : IGameEvent { public readonly OrderId Id; public readonly CustomerId Customer; public readonly RecipeId Recipe; }
public readonly struct OrderStateChanged : IGameEvent { public readonly OrderId Id; public readonly OrderState From, To; }
public readonly struct OrderServed       : IGameEvent { public readonly OrderId Id; public readonly float Quality01, Accuracy01, WaitSeconds; }

// Pho.Domain/Events/EconomyEvents.cs
public readonly struct CashChanged : IGameEvent { public readonly decimal NewBalance, Delta; public readonly LedgerCategory Category; }
public readonly struct DayEnded    : IGameEvent { public readonly int Day; public readonly DailyReport Report; }
```

**Unity-side ergonomics** (in `Pho.Core`) — prevents the #1 event-bus bug,
forgotten unsubscribes:

```csharp
public abstract class GameBehaviour : MonoBehaviour {
    protected GameContext Ctx { get; private set; }
    protected void On<T>(Action<T> h) where T : struct, IGameEvent => _subs.Add(Ctx.Events.Subscribe(h));
    protected virtual void OnDestroy() { foreach (var s in _subs) s.Dispose(); }
}
```

**Rule:** events are for *notification of facts that already happened*
(past-tense names). Commands (`ServeBowl`, `TakePayment`) go through service
interfaces, not the bus. Mixing the two is how event buses turn into
spaghetti.

## 4. Save architecture

### Root DTO

```csharp
// Pho.Save/Dto/SaveFile.cs — pure POCOs, Newtonsoft, public fields
public sealed class SaveFile {
    public int schemaVersion;                 // ALWAYS first, ALWAYS present
    public string gameVersion;                // "0.1.3" — informational only
    public long savedAtUnixSeconds;
    public WorldDto world;
    public EconomyDto economy;
    public InventoryDto inventory;
    public ProgressionDto progression;
    public RestaurantDto restaurant;
    public PlayerDto player;
}

public sealed class WorldDto     { public int day; public float timeOfDaySeconds; public string phase; } // Prep|Open|Closed
public sealed class EconomyDto   { public decimal cash; public List<DailyReportDto> recentDays; }        // last 7
public sealed class InventoryDto { public List<LotDto> lots; }
public sealed class LotDto       { public string ingredientId; public float quantity, qualityAtPurchase, freshness; public int purchasedOnDay; public string storage; }
public sealed class ProgressionDto {
    public List<string> unlockedRecipeIds;
    public List<string> ownedEquipmentIds;
    public Dictionary<string, decimal> menuPrices;    // recipeId -> price
    public float reputation;
    public Dictionary<string, bool> flags;            // tutorial/progression flags
}
public sealed class RestaurantDto { public float cleanliness01; public List<string> dirtyTableIds; }
public sealed class PlayerDto     { public Vec3Dto position; public float yaw; }
```

### Decisions

1. **Save only at a day boundary.** Autosave fires on `DayEnded`; manual
   save is disabled while the restaurant is Open. This eliminates
   serializing in-flight customers, partially-assembled bowls, NavMesh
   agent state, and mid-simmer broth — an enormous amount of complexity for
   zero vertical-slice value. Reloading always starts at "morning of day N."
2. **Only stable string IDs cross the boundary.** No `InstanceID`, no GUIDs,
   no object references. A missing ID on load is logged and skipped, never
   a hard crash.
3. **`decimal` for money**, everywhere. Float money produces `$9.499999` in
   the daily report.
4. **Not saved (deliberately):** restaurant layout (no build mode),
   employees, supplier relationships, skill levels, weather, individual
   customer memory.

### Migration

```csharp
public interface ISaveMigration {
    int FromVersion { get; }                   // migrates FromVersion -> FromVersion+1
    void Migrate(JObject root);                 // mutate the raw JSON tree
}

public sealed class SaveMigrator {
    public JObject MigrateToCurrent(JObject root, int currentVersion);   // applies chain, sets schemaVersion
}
```

Migrations operate on the raw `JObject`, so we never keep N generations of
DTO classes alive. Each migration ships with a golden fixture:
`Assets/Scripts/Tests/SaveTests/Fixtures/v1_typical.json` → assert it loads
at current version with expected values. This turns migration correctness
into a regression test rather than a hope.

### IO safety

```csharp
public interface ISaveStore {                       // pure — System.IO only
    bool TryRead(string slot, out string json);
    void Write(string slot, string json);            // tmp -> flush -> backup rotate -> atomic move
    bool TryReadBackup(string slot, out string json);
}
```

Load order: primary → on any exception, `.bak` → on failure, log a
`SaveCorrupted` event and start a new game. `FileSaveStore(rootPath)` is
constructed in `Pho.Core` with `Application.persistentDataPath`; tests use
`InMemorySaveStore`.

### Participation pattern

```csharp
public interface ISaveParticipant {                 // Pho.Domain
    void Capture(SaveFile save);
    void Restore(SaveFile save, IGameDatabase db);
    int RestoreOrder { get; }                        // inventory before kitchen, etc.
}
```

Each service (`InventoryService`, `EconomyService`, `ProgressionService`,
`DayCycleService`) implements it and self-registers via its installer.
**No shared save-wiring file** — critical for parallel work.

## 5. First-person interaction architecture

`Pho.Core/Interaction/` holds the interfaces (so `Pho.Kitchen` and
`Pho.Customers` do **not** depend on `Pho.Player`).

```csharp
public readonly struct InteractionContext {
    public readonly IInteractorAgent Agent;
    public readonly RaycastHit Hit;
    public readonly InteractionVerb Verb;      // Primary | Secondary
}

public interface IInteractorAgent {            // what a station is allowed to know about the player
    IHoldable Held { get; }
    bool HasFreeHands { get; }
    bool TryTake(IHoldable item);              // station -> hands
    bool TryGiveHeld(out IHoldable item);      // hands -> station
    Transform HoldAnchor { get; }
}

public interface IInteractable {
    string GetInteractionText(in InteractionContext ctx);   // "Press E to fill pot"
    bool CanInteract(in InteractionContext ctx);
    void Interact(in InteractionContext ctx);
}

public interface IHoldable {                    // carryable world object
    Transform Transform { get; }
    HoldPose Pose { get; }                      // TwoHandedLow | OneHandedFront | Tray
    bool AllowsSprint { get; }
    void OnPickedUp(IInteractorAgent agent);
    void OnDropped();
}

public interface IItemReceiver {                // counters, stations, tables, sinks
    bool CanAccept(IHoldable item);
    bool TryAccept(IHoldable item);
}

public interface IPlacementSurface {
    bool TryGetPlacement(Vector3 aimPoint, IHoldable item, out Pose placement);
}
```

**Deviation from GDD §46, deliberate:** the GDD's
`Interact(PlayerInteractor player)` couples every interactable to a
concrete player class. `InteractionContext` + `IInteractorAgent` decouples
it, makes stations testable with a fake agent, and lets employees (post-VS)
drive the same interactables with zero refactor.

**`PlayerInteractor`** (`Pho.Player`): one `SphereCast` per frame from
camera center (radius 0.12, range 2.5m, `Interactable` layer mask),
`GetComponentInParent<IInteractable>` with a per-collider cache, plus
hysteresis (must miss for 3 consecutive frames before clearing the
highlight) so the prompt doesn't flicker on edges. Publishes
`InteractionTargetChanged` for the UI; the UI never raycasts.

**Carry system:** single hand slot. Held items are **kinematic +
reparented** to `HoldAnchor` with a lerped local pose — no configurable
joints, no physics-driven carry. Physics carry looks great in videos and
produces a week of jitter bugs. Drop = re-enable rigidbody, apply a small
forward impulse. Placement = `IPlacementSurface` returns a snapped pose; a
`Physics.CheckBox` at the target rejects overlaps; a ghost material shows
valid/invalid.

**Cut from the vertical slice:** rotating held items (GDD §73). Add later;
it costs input plumbing and buys nothing for the loop.

## 6. State machines (pure C#, MonoBehaviour adapters)

### 6.1 Order state machine

```csharp
public enum OrderState { Created, Waiting, Accepted, Preparing, Ready, Served, Completed, Cancelled, Expired, Refunded }

public static class OrderStateMachine {
    static readonly Dictionary<OrderState, OrderState[]> Allowed = new() {
        [Created]   = new[]{ Waiting, Cancelled },
        [Waiting]   = new[]{ Accepted, Cancelled, Expired },
        [Accepted]  = new[]{ Preparing, Cancelled, Expired },
        [Preparing] = new[]{ Ready, Cancelled, Expired },
        [Ready]     = new[]{ Served, Expired, Cancelled },
        [Served]    = new[]{ Completed, Refunded },
        [Completed] = Array.Empty<OrderState>(),
        [Cancelled] = Array.Empty<OrderState>(),
        [Expired]   = new[]{ Refunded },
        [Refunded]  = Array.Empty<OrderState>(),
    };
    public static bool CanTransition(OrderState from, OrderState to);
    public static bool IsTerminal(OrderState s);
}

public sealed class OrderModel {
    public OrderId Id; public CustomerId Customer; public string TableId;
    public RecipeId Recipe; public OrderModifiers Modifiers;   // noOnion, extraMeat, size, spice
    public decimal QuotedPrice;
    public OrderState State { get; private set; }
    public float CreatedAtGameSeconds, ServedAtGameSeconds;
    public bool TryTransition(OrderState to, float nowSeconds, out string error);
    public float WaitSeconds(float now) => (ServedAtGameSeconds > 0 ? ServedAtGameSeconds : now) - CreatedAtGameSeconds;
}
```

**Deviation from GDD §62:** `RestaurantOrder.Customer` is typed there as a
`Customer` object reference. That makes the order unserializable and
untestable. We use `CustomerId`.

### 6.2 Customer state machine

The important trick: `CustomerBrain` is pure and drives the world through
an interface the MonoBehaviour implements. This makes the full customer
lifecycle unit-testable with a fake world — no NavMesh, no scene, no frame
timing.

```csharp
public enum CustomerState {
    Spawning, WalkingToEntrance, Queuing, WalkingToSeat, Sitting,
    BrowsingMenu, ReadyToOrder, WaitingForFood, Eating, Paying,
    Leaving, LeavingAngry, Despawned
}

public interface ICustomerWorld {                        // implemented by CustomerAgent (Pho.Customers)
    bool RestaurantIsOpen { get; }
    bool TryClaimSeat(CustomerId id, out SeatHandle seat);
    void ReleaseSeat(SeatHandle seat);
    void MoveTo(Vec3 destination);
    bool HasArrived { get; }
    Vec3 EntrancePosition { get; }
    Vec3 ExitPosition { get; }
    float Cleanliness01 { get; }
    OrderId PlaceOrder(CustomerId id, SeatHandle seat, RecipeId recipe, OrderModifiers mods);
    bool TryTakeServedDish(OrderId order, out ServedDish dish);
    void Pay(CustomerId id, decimal amount, decimal tip);
    void Despawn();
}

public sealed class CustomerBrain {
    public CustomerState State { get; private set; }
    public CustomerBrain(CustomerId id, ICustomerArchetype archetype, IBalanceConfig cfg, IEventBus bus, IRandom rng);
    public void Tick(float dt, ICustomerWorld world);
    public SatisfactionResult? Result { get; }           // set on Paying/LeavingAngry
}
```

`IRandom` is an injected interface (`SystemRandom` at runtime,
`SeededRandom` in tests) — **never `UnityEngine.Random`** — so customer
behaviour is deterministic and reproducible in tests.

`CustomerAgent : GameBehaviour, ICustomerWorld` owns the `NavMeshAgent`,
animation, and debug state label; it just calls
`_brain.Tick(Time.deltaTime, this)`.

**Simplifications for the vertical slice:** patience decays only while
`WaitingForFood` and `Queuing`; one customer per seat (no groups); one dish
+ no drink per customer initially; payment happens at the table (customer
transitions to `Paying`, player interacts to collect cash — preserves the
hands-on pillar without a cashier-walk pathing subsystem).

## 7. Cooking / bowl assembly model

### Bowl records exactly what went in

```csharp
public readonly struct BowlComponent {
    public readonly ComponentSlot Slot;      // Noodle | Broth | Protein | Aromatic | Herb | Garnish
    public readonly IngredientId Ingredient;
    public readonly float Amount;
    public readonly float Quality01;         // from the actual lot consumed
    public readonly float Freshness01;
    public readonly float AddedAtGameSeconds;
}

public sealed class BowlContents {
    readonly List<BowlComponent> _components = new();
    public IReadOnlyList<BowlComponent> Components => _components;
    public float BrothTemperatureC { get; private set; }
    public float AssembledAtGameSeconds { get; private set; }
    public bool IsSealed { get; private set; }           // set when placed on the pass

    public AddResult Add(in BowlComponent c);            // rejects if sealed / slot over-capacity
    public void Seal(float nowSeconds);
    public void CoolTowardsAmbient(float dt, IBalanceConfig cfg);
}
```

Every add comes from `InventoryModel.TryConsume(...)` → `ConsumedIngredient`,
so a bowl carries the true quality/freshness of the specific lot used.
Spoiled brisket is visible in the score with zero extra plumbing. This
directly satisfies GDD §75 ("A dish must record exactly what ingredients
were placed in it. Do not fake recipe completion by clicking a single Cook
button").

### Recipe matching — pure function

```csharp
public readonly struct Defect { public readonly DefectKind Kind; public readonly ComponentSlot Slot; public readonly IngredientId Ingredient; public readonly float Severity01; }
```

Algorithm (deterministic, no allocations in the hot path beyond the defect
list):
1. Group bowl components by `ComponentSlot`.
2. For each `RecipeComponent`: missing + required → `MissingRequired`
   (severity 1.0); present but outside `tolerance` → `TooLittle`/`TooMuch`
   scaled by the miss; wrong ingredient in a required slot →
   `WrongIngredient`.
3. Bowl components matching no recipe component → `ExtraUnwanted` (weight
   from config; garnish slots are cheap, protein slots are expensive).
4. `Accuracy01 = clamp01(1 - Σ(severity × cfg.defectWeight[kind]))`.
5. `BestMatch` runs steps 1–4 over the menu and takes the max — this is how
   the player finds out they made a Phở Chín when the customer wanted Phở
   Tái.

## 10. Parallelization plan

### The hard constraint first

**Only one process can hold the Unity `Library/` at a time.** Two agents
running Unity against the same folder will corrupt the asset database.

**What we'll actually run:** **one integration agent owns the only Unity
Editor + MCP connection**; 2–3 authoring agents write C# and run
`dotnet test` only. The integration agent pulls branches, compiles, runs
Unity tests, and reports failures back. Authoring agents never launch
Unity. (The alternative — one Unity instance per git worktree — works too
on 24GB but caps at 2 concurrent Editors; not worth it for this project
size.)

### Wave plan

**Wave 0 — strictly sequential, one agent (M0 + M1).** Nobody else starts.
Output is the frozen contract surface. Parallelizing this guarantees
interface churn that invalidates everyone's work.

**Wave 1 — 4 agents in parallel, zero file overlap:**

| Agent | Owns (exclusive write access) | Milestones | Unity needed? |
|---|---|---|---|
| **A — Logic** | `Assets/Scripts/Domain/**`, `Assets/Scripts/Save/**`, `Tests/DomainTests/**`, `Tests/SaveTests/**` | M4, M5(logic), M8(logic), M10, M11(logic), M12(logic) | **No** — `dotnet test` only |
| **B — Player** | `Assets/Scripts/Player/**`, `Assets/Scripts/Core/Interaction/**`, `Tests/PlayTests/Interaction*` | M2, M3 | Yes |
| **C — Content/Tools** | `Assets/Scripts/Data/**`, `Assets/Scripts/Editor/**`, `Assets/Content/**`, `Assets/Prefabs/**`, `Assets/Scenes/**`, `Tests/DataTests/**` | SO definitions, `ContentGenerator`, `SceneBuilder`, `PrefabBuilder`, NavMesh bake script | Yes |
| **D — UI** | `Assets/Scripts/UI/**` | HUD, prompt, order board, day summary, debug panels | Optional (can stub) |

Agent A is the biggest workload and needs no Unity — assign the strongest
agent there; it never blocks on the Editor.

**Wave 2 — 2 agents in parallel (needs A+B+C merged):**

| Agent | Owns | Milestones |
|---|---|---|
| **E — Kitchen** | `Assets/Scripts/Kitchen/**` | M5 (adapters), M13 |
| **F — Customers** | `Assets/Scripts/Customers/**` | M6, M7, M9 |

These only meet at `OrderService` (Core) — its interface is defined in
Wave 0, so they never touch the same file.

**Wave 3 — sequential, one agent.** M11 wiring, M12 wiring, M14 golden
path. Integration work is inherently cross-cutting; parallelizing it
produces conflicts.

### Shared files that will cause conflicts — and the mitigations

| File | Why it conflicts | Mitigation |
|---|---|---|
| `Core/GameContext.cs` | Every agent wants to add a service field | **Never edit it.** Type-keyed `ServiceRegistry`; each assembly ships its own `XInstaller.cs` and self-registers. |
| Bootstrap wiring | Adding an installer = scene edit | `GameBootstrap` **reflects** over loaded assemblies for `[AutoInstall]` types implementing `IInstaller`. Zero scene edits. |
| `Core/InstallOrder.cs` | Ordering constants | Accepted single shared file. Append-only, `const int` spaced by 100. |
| `*.unity`, `*.prefab` | YAML, unmergeable | **Generated by `Pho.EditorTools`.** On conflict: `git checkout --ours`, re-run the builder. Only Agent C edits builders. |
| `Assets/Content/*.asset` | YAML | Generated from a **C# manifest file**. Agents edit the manifest, never the `.asset`. |
| `.meta` files | GUID collisions if two agents touch one folder | Strict per-agent directory ownership (table above). |
| `Packages/manifest.json` | Package adds | **Only Wave 0** touches it. Later needs go through the integration agent. |
| `ProjectSettings/**` | Binary-ish | Wave 0 defines layers/tags via `Core/Layers.cs` + an applying editor script. Frozen after. |
| `InputSystem_Actions.inputactions` | JSON asset | Generated by a Wave-0 editor script from a C# spec. Frozen. |
| `*.asmdef` | Reference changes | Wave 0 defines the final dependency graph. Any later change is an architecture change — goes through the integration agent. |

### Rules of engagement

1. One branch per agent, rebased on `main` at least daily.
2. An agent may **read** any file; it may **write** only inside its owned
   directories.
3. `dotnet test` must be green before every push.
4. New event structs go in the owning agent's `Events/<Area>Events.cs` —
   never a shared file.
5. Anything requiring a new asmdef reference, package, layer, or
   ProjectSettings change → stop and escalate.

## 12. GDD deviations and scope cuts

**Architectural corrections:**

1. **§46 `IInteractable.Interact(PlayerInteractor)`** — concrete coupling
   would force a rewrite of every station once employees (Phase 13) arrive.
   Use `InteractionContext` + `IInteractorAgent` instead.
2. **§62 `RestaurantOrder.Customer` as an object reference** —
   unserializable, untestable, keeps despawned customers alive. Use
   `CustomerId`.
3. **§52/§71 flat `Scripts/` folders** — no assembly boundaries means a
   40-second compile per keystroke and no way to enforce purity. Same
   folder names, real asmdefs.
4. **`Resources/` in the folder plan** — ships in every build, invisible to
   reference analysis. Use `GameDatabase` referenced from the boot scene.
5. **Implied `JsonUtility` for saves** — no dictionaries, no
   missing-vs-default distinction, no polymorphism, no migration story. Use
   Newtonsoft (works in the pure assembly too).
6. **§64 "pool customers/dishes"** — premature at 3–5 concurrent customers;
   adds stale-subscription bugs for no measurable gain. `ICustomerFactory`
   keeps pooling a drop-in for later.

**Scope traps cut or reduced for the vertical slice:**

| GDD feature | Verdict |
|---|---|
| §55.2 wet-market shopping trip | **Cut the second location.** Replace with a supplier tablet + delivery crates in the same scene. Street/market is post-VS. |
| §49 "20–30 active NPCs" | **Cap at 5.** NavMesh baked via editor script, never hand-placed. |
| §18 Player energy | **Cut entirely** (already optional in the GDD). |
| §15 Cleanliness (7 dirt systems) | **Reduce to one:** dirty tables → single `Cleanliness01` float → satisfaction term. |
| §16 Health inspection | **Cut.** No dependency in the VS loop. |
| §14 Review text generation | **Cut.** Reputation is a single float from satisfaction. |
| §6.1 broth, 12 parameters | **Reduce to 4:** volume, aromatic set, simmer time, temperature. `BrothState` leaves room for the rest later. |
| §27–33 (weather, events, delivery, life sim, relationships, competitors, skills) | **All post-VS.** None appear in the §55 loop. |
| §75 "3 phở recipes" | **Build 2 first** (Tái, Chín), add Đặc Biệt once matching is proven. Same for archetypes: 2 first, then expand. |
| §50 save restaurant layout | **Drop.** No build mode in the VS. |
| §55.14 "buys one upgrade" | **Keep.** Only progression proof in the slice; cheap to build. |

**One risk worth naming:** `noEngineReferences: true` will be *annoying* —
an agent will want `Mathf.Clamp01` or `Vector3` in the domain and be
tempted to loosen the flag. Resist. `Pho.Domain/Math/MathP.cs`
(`Clamp01`, `Lerp`, `InverseLerp`, `Remap`) and `Vec3` ship in M1, before
anyone hits the wall. If that flag comes off, the fast test loop dies and
with it most of the value of this architecture.
